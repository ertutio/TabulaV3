# 自用版覆盖安装与旧数据验证步骤（任务3，2026-11-06）

适用：ertutio/TabulaV3 自用主线（fork 包名 `com.tabula.v3`、fork 签名 `forkRelease`、当前 versionName `3.3.5` / versionCode 5）。原则：**正式包验证不能由独立 debug 测试包替代**；每步先记录再操作，任何一步失败即停下登记，不带着未知状态继续升级。

## 前置

1. 固定来源：只从仓库 Actions 的 build 产物或本地 `./gradlew :app:assembleRelease`（forkRelease 签名）获取 APK；记录 APK SHA-256 与源码提交号。
2. 准备旧版本：当前在用的上一版安装包（或其已安装状态）；**不要**先卸载。
3. 备份（即使流程只做覆盖安装）：`adb pull /sdcard/Android/data/com.tabula.v3/files` 与分享目录；元数据 JSON（图集元数据、原图追踪）在应用私有目录，覆盖安装不清除，无需 root 提取，但记录 MediaStore 内容计数。

## A. 覆盖安装（同一签名，不清数据）

1. 记录升级前状态：
   - 图集列表与各图集数量（截图）；
   - 回收站条目数（应用内）；
   - 专清/整理断点：若正在整理中，记录当前图集/月份与剩余组数；
   - 系统图集（DCIM 等）未被应用改动的基准计数。
2. `adb install -r <new.apk>`（或系统安装器覆盖安装）；确认安装器未提示签名冲突。
3. 冷启动应用，验证：
   - 旧图集元数据完整（隐藏/屏蔽/颜色/排序在）；
   - 回收站条目数与升级前一致，恢复一张验证内容完好；
   - 整理断点续接：进入同一图集/月份，断点批继续而非重新开始；
   - 图集内图片缩略图正常（card_/grid_ 缓存键迁移后无串图、无全量重解码卡顿异常）。
4. 验证更新渠道行为：应用内更新检查提示与本 fork 渠道一致（不指向原仓库发布）。
5. 验证原作者来源/鸣谢入口仍在（关于页）。

## B. 旧数据语义抽查（升级后一次性）

1. **身份键迁移**：挑选一张升级前就在的照片，在系统图集层面确认其卷/ID；在应用内删除回收站一张、恢复一张，确认目标正确（不误删同数值 ID 的另一卷照片——跨卷双卡用户重点核对）。
2. **清理组 legacy 引用**：若升级前存在整理进度，检查组边界按组成员身份重算而非按旧组 id 整组失效（对照片按组逐张确认）。
3. **哈希缓存版本**：修改一张已归档照片的内容（外部编辑），确认相似组缓存不提供陈旧分组（ver_ 版本键失效路径）。
4. **偏好迁移幂等**：重启应用两次，确认冷却/专清进度不漂移、不重复处理。

## C. 回退（仅在 A/B 失败时）

1. 不卸载、不清数据：`adb install -r <old.apk>`（versionCode 更高时需 `-d` 允许降级，仅自用调试可接受）。
2. 记录失败步骤、截图、APK SHA-256 与源码提交号，登记到进度文件后再决定修复或放弃该版本。

## D. 边界（明确不做/待条件）

- 卸载后重装（清除私有目录）**不属于**覆盖安装验证，其数据丢失为预期行为，不作为升级缺陷登记。
- 跨签名安装（原版 Doryoku1223 包 ↔ fork 包）：签名不同必然失败，不属于本清单；两包共存验证仅需确认包名冲突提示正常。
- 首次签名发布流程（历史 3.3.4 的发布流程）不套用于新版本（C7/T13 门控）。
