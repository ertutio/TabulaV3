任务范围和持续执行规则见[总计划](../.ua/DEVELOPMENT_ROADMAP.md)，当前证据和 next_action 见[进度文件](../.ua/DEVELOPMENT_PROGRESS.md)。本文件是未来实现的通过条件，不表示这些检查已经执行。

## 把历史编号变成实际断言

本次迁移读取的 #9 路线图与 [.ua/agent-analysis.json 固定版本](https://github.com/ertutio/TabulaV3/blob/5948a448cc9cf258fc76ab56b8a86727e2cbbd10/.ua/agent-analysis.json) 只给出 TC01–TC55 的组级编号映射，没有逐例输入/断言定义；TC56–TC58 有明确规格。保持这些编号用于追踪，但不臆造某个旧 TC 的原义或直接将整段编号写成 PASS。以下组级要求是可执行范围；实施时给每个实际用例一个稳定 ID，记录关联 T 组及历史 TC 范围、输入、故障注入、预期与证据。若找到确切的旧规格，再追加精确映射。

例如：`C0-DETAIL-EMPTY-RETRY` 对应 T05 / TC23–TC26 范围，输入为首次详情查询失败且列表为空，要求错误和重试可见；重试成功后真实图片出现，切换图集后旧结果不覆盖新页面。这不是声称它就是某个唯一旧 TC。

## 选择并运行必要检查

1. 纯逻辑、持久化、故障分类或迁移：选择受影响的现有测试类，新增能暴露旧问题的用例，执行相应 Gradle 单测。记录真实命令及 XML 结果，避免只复制实现逻辑作测试。
2. 共享契约/调用链稳定后：集中执行所需 unit suite、编译/打包和必要集成检查。复用输入未变且覆盖相同断言的已有证据；代码、依赖、配置、环境或测试输入变更后只重跑受影响范围，强制 CI 仍执行。
3. UI/MediaStore/系统授权：运行真实 instrumentation，先确认设备和目标应用身份，再操作并核对结果、取消和重开。将未跑、跳过、assumption、崩溃、超时和夹具失败分别记录，整体绿色不能掩盖用例未执行。
4. Release/工具链/最终交付：按实际变更验证 R8、产物身份/签名、覆盖安装、持久恢复和目标设备；debug 测试包不同身份不能证明正式 `com.tabula.v3` 覆盖安装。

当前可复用的仓库入口（实施时先读实际配置）：

- [build-volume-confirmation.yml](../.github/workflows/build-volume-confirmation.yml)：Release 单测及 Release/debug/androidTest 构建、Release 身份/R8/体积检查，API36/37 真实 MediaStore 与 UI 探针。设备脚本为 [run-volume-device-probe.py](../tools/run-volume-device-probe.py) 和 [run-cloud-ui-probe.sh](../tools/run-cloud-ui-probe.sh)。
- [build-test-apk.yml](../.github/workflows/build-test-apk.yml)：debug 单测与独立测试包构建/签名。仅这一工作流成功不代表模拟器已运行。
- 当前通用设备入口支持 `workflow_dispatch`，push 仅匹配其配置中的特定旧分支，**开 PR 或 push 普通开发分支不保证触发验证**。确认已有授权后显式选择开发 ref 触发一次，等待实际 run，核对 `head_sha` 和所有需要的 job；分支随后变化则判断证据是否仍适用。

例如，经授权手动启动当前设备入口：

```sh
gh workflow run build-volume-confirmation.yml --repo ertutio/TabulaV3 --ref <实际开发分支>
```

命令返回只表示触发请求成功。先查询是否已存在相同 SHA 的合适运行，避免重发；用真实 run ID 保存证据，不能把可变分支名当测试过的 SHA。没有 CI 权限或设备环境时标明缺口，继续独立工作。

## 真实模拟器与测试夹具

- 保留 API36/37 的真实身份/镜像/工具版本和 AVD target 检查；API37 当前有效配置通过 cmdline-tools 22.0 创建 `android-37.0` target。未知元数据要明确，`android-0` 或平台进程异常不能当应用测试通过。
- 保留三个测试窗口的 boot_id、system_server/SurfaceFlinger PID/starttime 及目标 native/DeadSystem 检查。不要通过吞掉平台崩溃或关闭断言得到绿色；环境修复与应用改动分别验证。
- 现有旧探针 3 项、Cleanup 2 项、Restore 2 项是已验证的起点。新增场景时同步声明预期 case/数量并检查逐例结果与 skip，不能只提高/降低一个总计数阈值；原有效断言保持。
- 故障注入和删除仅对测试自建且有 manifest 的合成对象；记录 volume/id/随机 name/完整 relativePath，删除前准确匹配，删除后明确查询不存在，集合外哨兵保持，再独立清理。错误/空输出/null Cursor/解析失败不当作不存在。
- CloudFixtureCleanup 只服务 opt-in 模拟器测试的 `@After`：先销毁 Activity，独立 shell 精确清理，验证 shell 与应用查询；不授予生产应用 MANAGE_MEDIA、不改 app-op 或全程采用 shell permission identity。UiAutomation 字符串入口按空白分词，完整脚本封装必须保留真正退出/错误信息；不能把重定向当 content 参数。
- 自有媒体的测试成功不能证明他人媒体授权、多卷热拔插、所有进程死亡/真实断电或目标 OEM 行为。必要真实设备缺口明确列出，不能由 green unit 代替。

## 每次 PR 的证据与验收

PR 描述写清具体触发条件、前后行为、受影响接口与数据、关联 C/T/实际 case，列已执行/失败/未测以及回退方式；保存 CI URL、实际 SHA、环境、报告位置与缓存情况。依赖 PR 写明顺序；只提交本人的已确认变更，逐项核对范围。

`FROM-CACHE` 是复用结果，应写明；旧细分计划中的“已知某测试失败”仅是当时历史，不构成永久允许失败。遇到新的失败先诊断并记录，禁止删测试、把失败改 skip 或以不相关成功替代。

文档保存、commit、开 PR、一次 green 均是进度事件；更新[进度文件](../.ua/DEVELOPMENT_PROGRESS.md)的 next_action 后继续总计划。只有实际满足总完成条件，或已完成所有独立就绪项并留下准确外部阻塞时，才结束当前执行。
