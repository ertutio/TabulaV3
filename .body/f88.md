对应路线图 #83 第 5 项：**删除前查看「还剩哪个版本」**。

路线图要求"先做字节相同的副本，再验证视觉相似版本"。本 PR 交付第一步的完整链路（判定 + 摘要计算 + 界面提示 + 确认前复核），第二步的判定也已就位但**默认不启用**。

## 用户从哪里进入，改完能做什么

回收站 → 多选若干张照片 → 顶部标题下多出一行：

> 其中 N 张还留有字节相同的副本

看到这行就知道"我选的这些里，有几张其实还剩一份相同的内容"，可以先把副本挑出来再决定删哪张。

**这行只是提示**：不阻止删除、不改变任何删除流程、不弹二次确认。

## 关键实现与审计入口

**判定规则（`data/duplicate/DuplicateRules.kt`，纯逻辑）**

`findExactDuplicates` 按 `(sha256, size)` 分组找互为副本。四个刻意保守的口径：

| 口径 | 理由 |
|---|---|
| 大小也参与比较 | 摘要相同而大小不同说明摘要计算有问题，宁可**不**报 |
| 0 字节 / 空摘要不算"有意义" | 空文件互相"相同"没有价值，提示它们只会误导 |
| 已在回收站的不算"还剩一份" | 否则会提示一个其实也快被删掉的副本 |
| 跨卷同数值 ID 是不同照片 | 沿用 `卷\|ID` 身份契约；但字节相同就是**真的**互为副本 |

**确认前复核（`reverify`，路线图明确要求）**

用户确认删除时**必须**重新检查两件事：

1. 提示里的"另一份"此刻是否还读得到
2. 它是否也落在本次要删的集合里 —— 两份都要删时"还剩一份"的前提不成立

单测 `reverifyFailsWhenCopyWasAlsoSelected` / `reverifyFailsWhenCopyIsGone` / `reverifyPassesWhenCopyStillReadableAndNotSelected` 逐条钉住。

**摘要计算（`data/duplicate/ContentDigestCalculator.kt`）**

- 独立于仓库既有两处 SHA-256（`SystemAlbumSyncManager` 的复制证据、`AlbumManager` 的清理前深检），因为那两处都绑定各自业务流程，副本检测需要在任意照片集上按需计算
- 64 KiB 逐块计算，**不**把整张图读进内存（大图会 OOM）
- 块与块之间响应协程取消，用户翻页不被卡住
- 读不到的照片**不进入结果**而不是整体失败 —— 一张坏图不该让整页提示消失（对应路线图"部分授权下尤其如此"）

**界面与接入**

- `RecycleBinScreen` 新增 `duplicateCounts` / `duplicateDetails`，默认空 = 行为与改动前完全一致
- `SelectionModeTopBar` 标题下挂一行提示，措辞由 `buildDuplicateHint` 统一
- `MainActivity` 在回收站内容变化时后台扫描 —— **只扫回收站内的照片**，这是最可能被永久删除的一批；对全库做摘要代价太大且没有同等价值

**第二步（视觉相似版本）已就位但不启用**

`VisualCandidate` / `rankVisualCandidates` / `visualCandidatesFor`：dHash 汉明距离 ≤10 视为"可能是其他版本"，按距离排序、滤掉自身与重复对。这层**必须**带"可能"的语气，且不参与任何自动删除决策。界面尚未接入，等第一步在真机上验证过误报率再开。

**审计边界**：本 PR 不删除文件、不新增权限、不改现有删除/恢复流程。

## 人工验收路径（可复现）

前置：图库里有同一张图片的两个副本（例如同一文件复制到 `DCIM/Camera/` 和 `Download/`）。

1. 把两张都移入回收站（卡片上滑两次，或暂存清理）
2. 回收站 → 多选这两张
3. **预期**：顶部出现「其中 2 张还留有字节相同的副本」
4. 只选其中一张 → **预期**：「其中 1 张还留有字节相同的副本」
5. 选一张没有副本的照片 → **预期**：不出现该行
6. **反例**：把两张副本中的一张改为同名但内容不同（例如用编辑器重新保存）→ 重复步骤 2 → **预期**：不出现提示
7. **大片文件**：对一张 20MB+ 的 HEIC 走同样流程 → **预期**：不卡顿、不 OOM，提示正确
8. **部分授权**：只授予部分照片访问 → **预期**：读不到的照片不产生提示，其他照片的提示照常

## 审计意见修复（第 2 轮）

### 1. 副本查找范围

旧实现只在回收站内部两两比较，回答的是"站内还有没有一样的"，而不是审计要求的"**图库里还剩哪一份**"。

现在：以回收站待删照片的**大小**为筛，只把大小相同的图库照片纳入候选（先缩小范围，避免全库逐张算 SHA-256），再对这批候选与待删照片一起算全文摘要，且只输出回收站照片的库内副本。

### 2. 界面提示排除选中项

旧 `buildDuplicateHint` 只看"有没有副本"，两份都选中时仍提示"还留有副本"——**实际上删了就一份不剩**，这会误导用户删掉最后一份。

现在副本必须**不在选中集合里**才计数；两份都选中时不提示。签名从 `duplicateCounts` 改为 `duplicateDetails`（需要副本身份才能判断）。

### 3. 确认前真实复核

新增 `reverifyDuplicatesBeforeDeletion`，在 `deleteRecycleBinImages` 实际删除前调用，逐条检查：

- 副本仍在当前图库集合里
- 副本不在本次删除集合里
- 副本此刻**可读**，且**重算的 SHA-256** 与主图一致（防同名不同内容）

复核不通过只摘掉提示，**不阻止删除**——用户有权删任何东西，我们的责任是不要在"还有一份"的假象下让他删。

### 新增测试

- `DuplicateHintTest` 重写为 9 项，核心 `copyThatIsAlsoSelectedDoesNotCount` 与 `mixedSelectionCountsOnlySurvivingCopies`
- 新增 `DuplicateReverifyScenariosTest` **12 项**，逐个覆盖审计点名的六类场景：

| 审计场景 | 用例 |
