对应路线图 #83 第 4 项：**在现有相似组上做连拍选片**。

## 用户从哪里进入，改完能做什么

卡片页当前批次被判定为一个连拍组时，卡片上方出现一条「这批像连拍 / 去选片」的入口。

点进去是**对比选片页**：

- 三列缩略图，每格右下角显示拍摄时刻（`HH:mm:ss`），靠它分辨连拍顺序
- **先勾选要保留的**：勾选态蓝色边框 + 勾；未选态橙色蒙版，提示"将被回收"
- 「查看待移入回收站的 N 张」展开列表，每行可「改留这张」
- 「这组都留」一键全保留
- 底部实时显示「保留 X 张 · 回收 Y 张」，确认后走**现有回收站**，可恢复

改完之后：一组连拍不用一张张滑，先挑出要留的，剩下的批量进回收站。

## 关键实现与审计入口

**入口守卫（保守启发式）**

`BurstSelectionRules.looksLikeOneBurst`：时间跨度 ≤10 分钟（与 `SimilarGroupDetector.TIME_WINDOW_MS` 对齐）**且** 同一 bucket **且** ≥2 张。

这是刻意保守的选择：相似推荐模式在没有可用组时会回退到随机模式，那时这批照片互不相关；宁可不出入口，也不要把随机抽到的几张说成连拍让用户误删。

**组身份一致**

`groupFromBatch` 把批次包成 `SimilarGroup`，身份沿用既有 `SimilarGroup.id` 的内容寻址口径（成员身份键集合的 SHA-256）。同一批照片每次得到相同 ID，因此冷却记录与进度不会因重新进入而错乱。单测 `groupFromBatchUsesContentAddressedIdentity` 验证成员顺序无关。

**决策规则（`data/burst/BurstSelectionRules`，纯逻辑）**

| 输入 | 结果 |
|---|---|
| 勾选一张，组内 3 张 | 保留 1，其余 2 张进待回收 |
| 勾选全部 | 待回收 0，确认按钮禁用（没东西可删） |
| **一张都不勾** | 拒绝 `KeepNothing` —— 全删不在这个界面做 |
| 勾了不在组内的照片 | 拒绝 `KeepOutsideGroup`，不静默忽略 |
| 空组 | 拒绝 `EmptyGroup` |
| 组内有重复成员 | 拒绝 `DuplicateMembers` —— 否则"其余照片"判定有歧义 |
| 跨卷同数值 ID | 视为两张不同照片（`卷\|ID` 身份键） |

**进度语义（audit 重点，对应路线图"部分操作失败不应把尚未处理的组标成完成"）**

- **取消/返回**：什么都不提交，**不调用** `markSimilarGroupProcessed`，该组原进度保留，用户下次还能再进
- **确认**：先 `recycleBinManager.addAllToRecycleBin` 成功，**之后才**调 `markSimilarGroupProcessed`
- 写入失败：catch 住并提示重试，组**不会**被标成已处理，也不改 `allImages`

**回收站路径**

`RecycleBinManager.addAllToRecycleBin`，与卡片上滑删除完全相同，因此回收站恢复、删除确认、权限流程全部复用。本 PR 不删除文件、不新增权限。

**审计入口**

- `app/src/main/java/com/tabula/v3/data/burst/BurstSelectionRules.kt` — 全部判定
- `app/src/main/java/com/tabula/v3/ui/screens/BurstSelectionScreen.kt` — 对比界面
- `app/src/main/java/com/tabula/v3/MainActivity.kt` — `burstSelectionContent`（提交与进度语义）
- `app/src/main/java/com/tabula/v3/ui/screens/DeckScreen.kt` — 入口守卫与浮动条

## 人工验收路径（可复现）

前置：相机连拍一组 5 张（10 分钟内、同一相册），进入相似推荐模式。

1. 卡片页出现「这批像连拍 / 去选片」→ 点进去
2. **预期**：5 张缩略图，默认勾选最早与最晚两张（蓝框），中间三张橙色蒙版
3. 取消勾选最早那张 → **预期**：底部变「保留 1 张 · 回收 4 张」
4. 全部取消勾选 → **预期**：底部提示"至少勾选一张保留，才能确认"，确认按钮禁用
5. 重新勾选两张 → 「查看待移入回收站的 3 张」→ 展开 → 对其中一张点「改留这张」→ **预期**：变成保留，待回收变 2 张
6. 点返回（不确认）→ **预期**：什么都没变，卡片页那 5 张仍在，回收站没有新增
7. 重新进入 → 勾选 2 张 → 确认 → **预期**：Toast「保留 2 张，3 张已移入回收站」；卡片页不再出现这 3 张；回收站里能看到并可恢复
8. **进度语义验证**：确认后重新进入相似推荐 → **预期**：这一组**不会**立刻再次弹出（已进冷却）
9. **失败路径**：在确认瞬间强制杀进程 → 重开后 **预期**：这组**仍可再次进入**（未提交成功不算已处理）

## 审计意见修复（第 2 轮）

**问题**：入口用 `BurstSelectionRules.looksLikeOneBurst(currentBatch)` 按时间跨度与相册**猜**组，再 `groupFromBatch` 现造一个。造出来的组身份与检测器的内容寻址摘要无关——冷却、进度、持久化全都对不上。

### 修正

1. **`RecommendationEngine.getRecommendedBatchWithGroup()`**：相似推荐模式下把实际用到的 `SimilarGroup` 一并返回（`BatchResult(images, group)`）；随机漫步模式 `group` 为 null。
2. **`DeckScreen` 新增 `activeSimilarGroup`**：入口改用 `BurstSelectionRules.effectiveGroup(group, currentBatch)`，不再猜。
3. **`effectiveGroup` 剔除规则**：
   - 不在当前批次（已滑过 / 已归档 / 待删除）
   - 已不在图库（`stillPresent`）
   - 重复成员
   - 剔除后**不足两张就不出入口**
   - 身份沿用原组 `id`，不重算
4. **`looksLikeOneBurst` 保留但标注"生产路径不再使用"**，仅供既有单测与无组对象的兜底调用点。

### 进度推进（审计要求）

提交时核验回收站确实收下每一张：`movedKeys.containsAll(expectedKeys)`。任一张没落库 → **整组视为未完成**：

- 不调 `markSimilarGroupProcessed`
- 不改 `allImages` / `imagesForSorting`
- 提示重试，用户可再次进入

核验通过后才标记 + `invalidateSimilarGroupCache` + 清空 `activeSimilarGroup`。
